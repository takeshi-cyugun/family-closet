# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"ファミリークロゼット" (Family Closet) — a family clothing-inventory app (Vision AI auto-tagging, family sharing, multi-language). Full spec: `要件定義書.md` (root, Japanese, V10). It describes a target architecture of `apps/web` + `apps/admin` + `packages/database|ui|i18n|config` under Turborepo — **only part of that exists today** (see "Spec vs. reality" below).

## Commands

Run from repo root unless noted (pnpm workspace, defined in `pnpm-workspace.yaml`: `apps/*`, `packages/*`).

- `pnpm dev` — runs `apps/web` dev server (port 3000) via `pnpm --filter web dev`
- `pnpm build` — builds `apps/web` via `pnpm --filter web build`
- `pnpm --filter web lint` — ESLint (flat config, `eslint-config-next`) for `apps/web`
- `pnpm --filter @repo/database db:push` — pushes `packages/database/src/schema.ts` (Drizzle) to whichever Postgres `DATABASE_URL` currently points at (local Supabase stack or the hosted project, depending on `apps/web/.env.local` / `apps/admin/.env.local`). To push to the hosted project without editing `.env.local`, prefix the command with an inline override, e.g. `DATABASE_URL="postgresql://...db.<project>.supabase.co:5432/postgres" pnpm --filter @repo/database db:push` (PowerShell: `$env:DATABASE_URL="..."; pnpm ...`). **After running this, restart any already-running `apps/web` dev server** — `packages/database` is consumed via a raw TS path alias (not a real `node_modules` workspace dependency, see "Spec vs. reality" below), so Turbopack's dev-server HMR does not reliably pick up schema changes there; a running server will keep throwing `column "X" does not exist` against a column that demonstrably exists (confirmed via direct `psql`) until it's restarted.
- No test framework is configured anywhere in the repo (no test script, no test runner dependency) — don't assume Jest/Vitest exist.
- `npx supabase start` (from repo root, requires Docker) — boots a local Supabase stack (Postgres, Auth, Studio on :54323, and a fake mail-capture inbox on :54324) per `supabase/config.toml`. `apps/web/.env.local` and `apps/admin/.env.local` both point at this local stack by default; the hosted project's credentials are kept commented out in `apps/web/.env.local` for switching back.
- `pnpm --filter admin dev` — runs `apps/admin` dev server (port 3001). `pnpm dev` (root) still only runs `apps/web`; there's no combined `dev:all` script, run both filters in separate terminals if you need both apps.
- `pnpm --filter admin build` / `pnpm --filter admin lint` — same pattern as `web`.

## Spec vs. reality (read before trusting other docs)

`.claude/AGENTS.md` and `apps/web/CLAUDE.md`/`AGENTS.md` describe the target design from `要件定義書.md`, not always current state. Known gaps as of this writing:

- No `packages/ui`, no `packages/config` — only `apps/web`, `apps/admin`, `packages/database`, `packages/i18n` exist. `apps/admin` is a minimal MVP (see "apps/admin" below), not the full spec (no 2FA, no IP allowlist, no audit log yet).
- No Turborepo — no `turbo.json`, no `turbo` dependency anywhere, despite it being referenced in the other docs.
- `packages/database`'s workspace name is **`@repo/database`**, not `@family-closet/database`. Import it as `@repo/database`; the mapping is a TS path alias in `apps/web/tsconfig.json` (`../../packages/database/src/index.ts`), not a `package.json` dependency — don't add it as a dependency expecting node_modules linking, the path alias is what makes it resolve.
- `packages/i18n` has **no `package.json`**, so it isn't a real pnpm workspace member and nothing imports it. `apps/web` does its own i18n instead (see below). Treat `packages/i18n` as an unused scaffold, not a live dependency.
- `apps/web/proxy.ts` (renamed from `middleware.ts` on 2026-08-07, exporting `proxy` instead of `middleware`) — confirmed against `apps/web/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md` and `next/dist/build/index.js` that the installed Next 16.2.12 actually emits the deprecation warning and resolves `proxy.ts`/`export function proxy` per the official `middleware-to-proxy` codemod; the file convention and export name both changed for real in this version, this note previously said otherwise and was wrong.
- `supabase/config.toml`'s `[auth.email.smtp]` block documents the production relay (Resend, `smtp.resend.com`, sender `noreply@family-closet.com` on the Resend-verified `family-closet.com` domain) but is deliberately kept `enabled = false` and is **not** pushed via `supabase config push` — it's reference/documentation only. The real values are entered directly in the Supabase Dashboard (Authentication → Emails → SMTP Settings) on the hosted project, so that local `supabase start` keeps using `[local_smtp]` (the fake inbox on :54324) instead of trying to send real mail. さくらインターネットのSMTP中継を最初に試したが、Supabase(海外の送信元)からの接続がタイムアウトし `auth.signUp()` が `AuthRetryableFetchError`(HTTP 504)で失敗したため、Resendに切り替えた — don't reintroduce さくらSMTP for production auth email without first confirming connectivity from Supabase's sending infrastructure.

## Architecture

### Auth is real (Supabase Auth); clothes data is real; guest-only bits are still mock

As of the 2026-08-04 "認証系実装" commit, auth is no longer mocked. `apps/web/app/_lib/auth.ts` (the old `MOCK_ACCOUNTS` module) and the auth-related parts of `apps/web/app/_lib/session.ts` were deleted; `session.ts` now only holds the guest-trial helpers (`startGuestSession`/`getGuestDaysLeft`, still `localStorage`-based — that part is intentionally client-only, guests aren't real accounts).

- **Login/signup/password flows are real Server Actions backed by Supabase Auth.** `apps/web/app/actions/login.ts` (`loginFamily`) looks up the member's `authUserId` in Postgres, then calls `auth.signInWithPassword` against Supabase Auth; on success it sets real httpOnly cookies (`family_id`, `member_db_id`, and — only when `members.isFirstLogin` is true — `fc_force_password_change`, which `apps/web/proxy.ts` still checks to force-redirect to `/change-password`). `actions/registerFamily.ts` calls `auth.signUp` (email confirmation required) and rolls back the Auth user if the DB-side write fails; `actions/addMember.ts` uses the Supabase admin client (`auth.admin.createUser`) with a synthetic `@members.familycloset.internal` email and an auto-generated initial password (added members don't need a real inbox); `actions/changePassword.ts` re-verifies the current password via `signInWithPassword` before calling `auth.admin.updateUserById`. Brute-force lockout (5 failed attempts / 5 min) is enforced server-side via the new `loginAttempts` table, keyed by both account and IP.
- **Clothes CRUD is wired to real Postgres/Supabase via Drizzle.** `apps/web/app/actions/clothes.ts` imports `db`/tables from `@repo/database` and performs real inserts/updates/deletes against `DATABASE_URL` (see `apps/web/.env.example` for the required env vars: Supabase URL/anon/service-role keys, `DATABASE_URL`, `GEMINI_API_KEY`). `packages/database/src/schema.ts` (Drizzle) is the source of truth for the data model: `families`, `members`, `clothes`, `subscriptions`, `loginAttempts`, with `familyId`-scoped multi-tenancy (RLS is a spec requirement — not yet enforced by any visible policy in this codebase, so don't assume it's active). `createClothes` returns `{ success: false, error, reason: 'item_limit' }` when the family's plan item-count cap is hit; `ClothesForm.tsx` shows a modal (not inline error text) with a CTA to `/signup` (guest) or `/settings` (existing member on a paid-tier cap) rather than surfacing the raw error string.
- **`apps/web/app/actions/startGuestSession.ts` is currently dead code** — nothing imports it. The "まずはお試し（登録不要）" button on `app/page.tsx` calls `startGuestSession` from `app/_lib/session.ts` instead (a `localStorage`-only stub that just timestamps trial start, does **not** touch the DB) and fires `router.push('/dashboard')` without awaiting it. The real guest `families`/`members` row only gets created lazily, the first time `ensureGuestFamily()` is actually called (e.g. `ClothesForm.tsx` mounting on `/clothes-new`) — this is why `/settings` shows "まだファミリーが作成されていません" until the user has visited the add-item screen at least once. This was flagged and the user explicitly chose to keep current behavior (confirmed 2026-08-07) rather than eagerly create the DB row on the top-page button click — don't "fix" this without asking first.
- `apps/web/app/_lib/clothes.ts` still has a large block of mock clothes/member data — check whether a given screen reads from that mock module or from the real `actions/clothes.ts` before changing data logic; the two coexist.
- Outbound auth email (signup confirmation, etc.) works end-to-end in production (`/register` confirmed working on Vercel), currently via Supabase's default mailer while Custom SMTP is being switched over to Resend — see the `supabase/config.toml` SMTP note above.

### apps/admin (運営者向け管理画面, MVP)

Added 2026-08-05. Separate Next.js App Router app (port 3001, its own `package.json`/`tsconfig.json`/Tailwind setup, not part of any Turborepo since none exists), matching the 要件定義書.md §1.4/2.2 intent of keeping the Service Role Key confined to `apps/admin` only — `apps/web` never imports `createSupabaseServerClient` for admin-privileged bulk reads.

- **Auth is deliberately NOT Supabase Auth.** There is exactly one admin account, defined by `ADMIN_EMAIL`/`ADMIN_PASSWORD` env vars (not a DB row, not an `auth.users` entry). `app/actions/auth.ts`'s `loginAdmin` compares against those env vars and sets an httpOnly `admin_session` cookie whose value is `HMAC-SHA256("admin-session", ADMIN_SESSION_SECRET)` (see `app/_lib/session.ts`); `isAdminAuthenticated()` recomputes and constant-time-compares it. There is no session table and no per-admin identity — this only works because there's a single operator account. If a second admin is ever needed, this needs to become real per-user auth first.
- **No middleware.ts.** Auth is instead enforced by `app/(protected)/layout.tsx`, a Server Component that calls `isAdminAuthenticated()` and `redirect('/login')`s if it fails. Every page under the `(protected)` route group inherits this guard; `/login` sits outside the group and is the only public route.
- **§9 non-functional requirements (2FA/TOTP, IP allowlist "Zero Trust", tamper-proof audit log) are explicitly NOT implemented yet.** This was a scoped-down MVP per user request ("とりあえずファミリー管理一覧画面"); don't assume they exist when touching this app.
- `app/actions/families.ts`'s `getFamilies()` is the first (and currently only) admin data view: joins `families`/`members`/`subscriptions` via Drizzle, then does a single `adminClient.auth.admin.listUsers({ perPage: 1000 })` call (not per-row) to resolve each family owner's email from `members.authUserId`. Rendered by `app/(protected)/page.tsx` → `_components/FamiliesTable.tsx`, a plain read-only PC-only table (user explicitly said mobile/responsive isn't needed for this app).
- Deploy plan (not yet done): a second Vercel project pointing at `apps/admin` as its root directory, initially on its default `*.vercel.app` domain, then cut over to a custom subdomain of `family-closet.com` (e.g. `admin.family-closet.com`) the same way `apps/web` did — `admin.<something>.vercel.app` is not obtainable since `vercel.app` isn't a domain the project owns.

### Vision AI

`apps/web/app/api/analyze-image/route.ts` is a Route Handler that sends an uploaded image to Gemini and returns `{ success, name, category, color, season }` as JSON. `ClothesForm.tsx` calls it directly (`fetch('/api/analyze-image', ...)`, field name `image`, plus a `language` field carrying the current `LanguageCode`) and uses the response to prefill the name/category/color/season fields; `apps/web/app/_lib/clothes.ts`'s `mapAiSeasonToSeason` reconciles the AI's free-text season words (in whatever language was requested) back onto the app's fixed internal season keys (通年/春/夏/秋/冬/春夏/秋冬).

- **Model:** `gemini-3.1-flash-lite` (not `gemini-1.5-flash` — that model was retired by Google and returns 404; confirmed via the `ListModels` endpoint that `gemini-3.1-flash-lite` is current. Matches the model used by a separate sibling project, `C:\Users\tcyug\develop\Closetton`, whose prompt/output shape this route was deliberately aligned with).
- **Language-aware output:** the prompt instructs Gemini to return `name`/`category`/`color` in the caller's language, and `season` using that language's words for spring/summer/autumn/winter/all-year (comma-separated if multiple) — `mapAiSeasonToSeason` builds a reverse lookup from `getDashboardDictionary(language).seasons` (plus the native Japanese keys as a fallback) to resolve those back to the internal keys.
- **`GEMINI_API_KEY` must be a real, currently-valid Google AI Studio key** — a stale/invalid key produces a generic `画像のAI解析に失敗しました。` 500 with no further client-side detail; check the dev server log for the underlying `[GoogleGenerativeAI Error]` message (`API_KEY_INVALID` vs. a 404 on the model name are different root causes).

### i18n — no dictionary package, per-route translation files

Despite `packages/i18n` existing, `apps/web` doesn't use it. Instead:
- `apps/web/app/_lib/i18n.ts` defines the shared `LANGUAGES`/`LanguageCode` type (ja/en/zh-CN/zh-TW) and `apps/web/app/_lib/LanguageContext.tsx` is the client-side provider (persists choice to `localStorage`, key `familyCloset.lang`).
- Individual routes maintain **their own** translation-string files that import only the `LanguageCode` type from the shared module (e.g. `apps/web/app/dashboard/_lib/i18n.ts`, `apps/web/app/settings/_lib/i18n.ts`) — there is no single central dictionary. When adding translated UI to a new route, follow this per-route pattern rather than trying to route through `packages/i18n`.
- No URL language prefixes (`/dashboard`, not `/ja/dashboard`) — this part matches the spec.
- **Language dropdowns list 日本語 last, not first.** `LANGUAGES` (in `_lib/i18n.ts`) is ja-first (used for lookups/type ordering), but every language *picker* UI (`app/page.tsx`'s `FOOTER_LANGUAGES`, `settings/_components/LanguageSection.tsx`'s `SORTED_LANGUAGES`) re-sorts to put ja at the end before rendering the option list. Reuse `LANGUAGES` directly for lookups (`.find(...)`), but build a ja-last array for anything the user picks from.

### Routing structure

`apps/web/app/` is Next.js App Router. Clothes detail (`/clothes/[id]`) is implemented twice on purpose: as a normal page (`app/clothes/[id]/page.tsx`) and as a modal via a parallel/intercepting route (`app/@modal/(.)clothes/[id]/page.tsx` + `app/@modal/default.tsx` + `app/_components/Modal.tsx`) so it opens as an overlay when navigated to from the dashboard grid but as a full page on direct load/refresh. Keep both in sync when changing the detail view.

**Clothes edit (`/clothes/[id]/edit`) is deliberately NOT a modal** (as of 2026-08-07) — there is only `app/clothes/[id]/edit/page.tsx` (a normal full page, `Header`+`BottomNav`, same shell as `/clothes-new`). An intercepted `app/@modal/(.)clothes/[id]/edit/page.tsx` used to exist but was removed: soft-navigating from inside the `@modal` slot to a route with no matching intercepted page is a known Next.js parallel-routes gap — the `@modal` slot resets to `default.tsx` (closes) but the `children` slot does **not** pick up the new URL, so the app appeared stuck on the dashboard even though the URL bar showed `/clothes/[id]/edit`. `ClothesDetailContent.tsx`'s "編集する" button works around this by using `window.location.href` (a real navigation) instead of a Next.js `<Link>`/`router.push`. If you ever reintroduce a modal edit route, you'll hit the same bug.

Server logic lives in `app/actions/` (Server Actions, `'use server'`) and `app/api/` (Route Handlers) inside `apps/web`, per the convention in `apps/web/AGENTS.md`.

### Settings screen hides raw IDs; guest defaults are localized at creation time

`apps/web/app/settings/` no longer exposes `families.id` / `members.member_id` (the login-facing identifiers) anywhere in the account-info card or the family member list — see `AccountInfoCard.tsx` and `MemberSection.tsx`. Instead:

- `families` has a `name` column (text, default `'ファミリー名'`, added 2026-08-07) — a separate, editable display name from the login `id`. `members.displayName` was already separate from `members.memberId`.
- Both are self-editable via `actions/settings.ts`'s `updateFamilyName`/`updateMemberDisplayName` (cookie-scoped to the caller's own family/member — no arbitrary target).
- **Guest sessions get language-correct defaults at creation time, not via display-time branching.** `actions/ensureGuestFamily.ts` takes a `language: LanguageCode` param and picks the family name / member name from small `Record<LanguageCode, string>` maps (`GUEST_FAMILY_NAMES`/`GUEST_MEMBER_NAMES`) before inserting — so an English-language guest session gets `"Guest Family"`/`"Guest"` in the DB from the start, not the Japanese literal `"ゲスト"`. Every caller of `ensureGuestFamily()` (all in `ClothesForm.tsx`) must pass the current `language`. Do not reintroduce `member.name === "ゲスト" ? ... : ...`-style display branching to work around missing localization here — fix it at the `ensureGuestFamily` call site instead. (Guest sessions created before this fix still have the Japanese literal stored and will keep showing it until a new guest session is started — this is accepted stale data, not a bug to chase.)
- `settings/_components/MemberSection.tsx`'s "add member" UI was stripped down to a single QR-code button per user request — the display-name/member-ID inputs and the `addMember` server-action call were removed from the UI. `actions/addMember.ts` itself still exists (issues a synthetic-email Supabase Auth user + initial password) but nothing currently calls it — it was superseded by the QR flow below, not dead code left over from before a decision was made.
- **The QR-invite flow is implemented (as of the "メンバー追加QRコード実装" commit), not undecided.** `actions/invite.ts`'s `getOrCreateInviteToken()` issues one persistent, non-expiring invite token per family (`families.inviteToken`, `crypto.randomBytes(24)`-based, generated lazily on first request and reused afterward — no rotation/revocation exists). `MemberSection.tsx` shows it as both a QR code (`InviteQrCode.tsx`, via the `qrcode` package) and a copyable URL of the form `/join/[token]`. That route (`app/join/[token]/page.tsx` + `JoinForm.tsx`) requires no login: `actions/joinFamily.ts`'s `lookupInviteToken` validates the token and checks the plan's member-limit before rendering the form, and `joinFamily(token, displayName)` inserts a new `member` row (role `member`, no Supabase Auth user — synthetic-email accounts are only created via `addMember.ts`, which this flow does not use) and sets the same `family_id`/`member_db_id` cookies as a normal login, landing the new member straight on `/dashboard`.

### Clothes detail screen: single edit button, no inline status toggle/delete

`ClothesDetailContent.tsx` (`/clothes/[id]`, both the full-page and `@modal` variants) intentionally shows only an "編集する" button — no one-tap status-toggle buttons and no delete button on this screen, even though `actions/clothes.ts`'s `updateClothesStatus()` exists for that purpose (currently unused — left in place for potential future use, don't assume it's wired up anywhere). Status changes and deletion both happen one step further in, inside `ClothesForm.tsx`'s edit mode (`/clothes/[id]/edit`): the status `<select>` there doubles as the status-change control, and a "削除する" link opens an in-page confirm dialog that calls `deleteClothes()`. This was confirmed as the intended design (2026-08-08), not a gap to fix — don't add detail-screen status/delete controls without asking first.

### Clothes photo pipeline: rotation is baked in server-side, thumbnails are real

As of 2026-08-08, `actions/uploadImage.ts`'s `uploadClothesImage()` does real image processing via `sharp` (added as an `apps/web` dependency), not a raw pass-through: it EXIF-auto-orients, then applies the user's chosen 90°-multiple rotation (`sharp(buffer).rotate().rotate(degrees)` — confirmed these compose correctly rather than one overriding the other), and produces two separate WebP outputs — a main image (long edge ≤1600px, quality 82) and a thumbnail (long edge ≤300px, quality 65, matching 要件定義書.md §5.4's "長辺約300px" target) — uploaded to fixed, `assetId`-keyed storage paths (`upsert: true`, so re-rotating overwrites the same files instead of leaving orphans). `clothes.thumbnailUrl` is a genuinely distinct, smaller asset now (previously it was just a copy of `imageUrl`).

- `ClothesForm.tsx` generates `assetId` client-side via `crypto.randomUUID()` when a file is first selected and keeps the original `File` in state so each rotate-button click re-runs the same server action with the new angle (not just a CSS preview transform — the CSS `rotate()` on the local object-URL preview is still used for *instant* visual feedback while the real reprocessing round-trip is in flight). Rotating an already-saved photo in edit mode (no freshly-picked `File`) is also supported: the first rotate click `fetch()`es the currently-stored image client-side, wraps it in a `File`, and feeds it into the same pipeline.
- `ClothesCard.tsx` (dashboard grid) now renders `item.thumbnailDataUrl` (falling back to `photoDataUrl`) with `loading="lazy"`; `ClothesDetailContent.tsx` still renders the full-resolution `photoDataUrl`, per spec. `ClothesItem.thumbnailDataUrl` and `actions/clothes.ts`'s `toClothesItem()` mapping (`row.thumbnailUrl ?? row.imageUrl`) were added for this.
- Blur-up placeholders and swipe-gesture-driven lazy loading (also mentioned in 要件定義書.md §5.4) are still not implemented — only the thumbnail generation and basic `loading="lazy"` landed.
